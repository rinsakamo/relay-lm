# Release Distribution Contract

Status: REL1 build/install contract for RelayLM v1. Owning Issue: #1447.

This contract freezes the mechanical distribution boundary only. It does not select cognitive defaults, redefine runtime configuration/operator semantics, choose a publication channel, or declare RelayLM 1.0 globally release-ready.

## Supported artifacts

The current source distribution authority is `pyproject.toml` with Hatchling as the PEP 517 build backend. REL1 supports exactly two local distribution artifact types:

- a wheel containing the `relaylm` Python package;
- a source distribution (`sdist`) capable of producing/installing the same package through the declared build backend.

The package name is `relaylm`. Package metadata resolves its version dynamically from the release-owned source at `src/relaylm/_version.py`; see `release-identity.md`. REL1 does not infer a public release tag from the current development version.

Hatch reproducible-build mode is explicitly enabled. REL1 CI proves byte-for-byte equality for two consecutive wheel/sdist builds of the exact same transaction head in the same build environment. This is a bounded build-mechanics proof, not yet the full REL2/REL3 immutable release identity or long-term toolchain pinning policy.

## Package metadata and runtime dependencies

Current metadata declares:

- Python: `>=3.12`;
- runtime dependencies: `PyYAML>=6.0.2`, `fastapi>=0.115`, `httpx>=0.28`, `uvicorn>=0.34`;
- console entrypoints: `relaylm = relaylm.cli:main` and `relaylm-eval = relaylm.evaluation:main`.

The package metadata lower bound is not, by itself, a claim that every newer Python, operating system, CPU architecture, or optional dependency combination is release-qualified. Current REL1 mechanical CI evidence is CPython 3.12 on GitHub-hosted Ubuntu. Broader release support requires explicit evidence rather than inference from a wheel filename or metadata range.

## Included-file boundary

The wheel contains the runtime `relaylm` package, the bounded first-party Starter Cognitive Package resources owned by #1891 under `relaylm.starters`, and wheel metadata generated by the build backend.

The sdist contains the source package needed to build that wheel plus the project build/readme/license metadata required for a source distribution. Hatch may also include its always-required source-distribution metadata files.

These repository surfaces are intentionally not distribution runtime authority and must not be promoted into the wheel or sdist by REL1:

- `tests/`;
- `docs/`;
- repository `examples/`;
- `evaluation/` repository evidence/fixtures;
- `.github/` workflows;
- `constraints/` development/test constraints.

Arbitrary user Cognitive Package content is external user/product data and is never implicitly bundled. The four first-party Starter roots are a deliberate Core 1.0 product exception: RelayLM owns those small inspectable resources as onboarding surface. They contain portable semantic package data only, not provider credentials, provider endpoints, physical model IDs, host policy, or other runtime-machine configuration.

## Fresh non-editable installation proof

The v1 `package-smoke` job validates the exact artifact produced from the exact transaction head. It must:

1. verify the checked-out commit is the event's exact head;
2. resolve the authoritative source package version before building;
3. build wheel and sdist twice and compare exact bytes within the same build environment;
4. inspect wheel/sdist filenames, metadata, entrypoints, required package files, and forbidden repository-only roots;
5. require built metadata and installed runtime version surfaces to match the authoritative source version;
6. install the built wheel into a fresh virtual environment without editable mode;
7. change working directory outside the repository checkout;
8. execute installed `relaylm --version`;
9. execute installed non-generative `relaylm doctor` against a scratch package and runtime config created outside the checkout;
10. execute installed `relaylm-eval` and require a passing native evaluation report;
11. install the exact built sdist into a second fresh environment without editable mode;
12. execute installed `relaylm --version` and `relaylm doctor` from outside the checkout;
13. run `pip check` in both installed environments.

The scratch package and runtime config are release-smoke inputs only. They are created at CI runtime outside the repository and are not distributed package data or Starter semantic authority.

## First-party Starter installed-artifact proof

#1891 additionally owns `.github/workflows/v1-starter-package-smoke.yml`. On the exact transaction head it builds both supported artifacts, asserts the complete first-party Starter resource set is present, installs each artifact non-editably into a fresh environment, changes execution outside the source checkout, and uses the installed `relaylm.starters` API to materialize all four roots to ordinary external filesystem directories.

For both wheel and sdist installations, that smoke then validates all four materialized roots through the production Cognitive Package loader and installed `relaylm doctor` path. It also reaches production `serve` startup assembly for one Character-like Starter (`relm`) and one machine-like Starter (`fact-summarizer`) while replacing only the final blocking server runner. No provider network call or source-checkout Python import is required for this acceptance.

This Starter smoke is product acceptance layered on top of REL1's general package mechanics. It does not redefine #1446 runtime semantics or #1889 Profile routing.

## Repository-relative assumptions

A supported installed command must resolve Python code, runtime dependencies, and first-party Starter resources from the installed artifact/environment, not from the source checkout. REL1 therefore executes installed commands with the current directory set outside the checkout.

Repository examples and developer test fixtures may exist, but the installed runtime cannot require them. First-party Starter resources are canonical package data under `relaylm.starters` and are materialized into user-owned filesystem roots before use.

## Relationship to #1446, #1890, #1891, and #1388

REL1 consumes the merged #1446 operator path and #1890 Cognitive Package root boundary. `doctor` is suitable for installed-artifact smoke because it performs configuration/package/runtime-assembly preflight without provider generation or semantic package mutation. #1891 owns the content and installed-use acceptance for first-party Starters; release engineering consumes that surface rather than redefining package semantics.

#1889 separately owns Cognitive Profile configuration and the public OpenAI `model` routing meaning. Its absence does not make Starter artifacts repository-relative or invalid, and this distribution contract does not claim unfinished Profile routing is already released.

#1388 still owns every calibrated cognitive default/profile. REL1 supplies no numeric value or profile and does not make successful packaging evidence a calibration claim. Final ordinary installed startup with canonical defaults remains dependent on the current #1388/#1446 authority.

## Deferred release mechanics

REL1 does not freeze:

- the remaining package version/tag/commit immutable identity policy beyond the single package-version source (REL2);
- exact release-candidate provenance and artifact acceptance workflow beyond this build/install foundation (REL3);
- publication registry/channel, credentials, signing, yank, rollback, or reissue mechanics (REL4);
- the final RelayLM 1.0 readiness decision (#1449).

No artifact produced by REL1 alone should be described as the public RelayLM 1.0 release.
