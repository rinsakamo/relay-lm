# SOUL Lab Management Read Contract

## Authority summary

This contract owns the exact current **read-only SOUL Lab management boundary** for:

```text
GET /lab/api/settings
GET /lab/api/characters
```

The current server implementation anchors are:

```text
relaylm/soul_lab_management.py
relaylm/soul_lab_app.py
```

The exact current projection schemas are:

```text
relaylm.lab.settings.v0
relaylm.lab.characters.v0
```

The boundary is deliberately narrow:

```text
validated RelayLM runtime configuration
  + loopback-configured server
  + actual loopback ASGI peer
  -> server-owned bounded projection
  -> Cache-Control: no-store
  -> browser read
```

It does not provide settings writes, character writes, connection tests, process actions, memory inspection, or semantic mutation.

## Relationship to permanent UI architecture

`docs/architecture/ui/soul-lab.md` owns the stable browser/server authority model for SOUL Lab.

That architecture explicitly does not own exact API fields or route schemas.

This document owns only the exact current management-read API and projection contract below that stable architecture.

## Historical implementation provenance

The SOUL Lab UI-A6 shared shell / Settings and UI-A7 management projection implementation handoffs are retired and no longer exist as live documents.

Current ownership is:

```text
exact current management-read responsibility

UI-A6 / UI-A7 implementation chronology
  -> Git history plus the central retirement manifest only
```

No implementation handoff remains current authority for this boundary.

## ASGI ownership

The SOUL Lab server entry point is the wrapper:

```text
relaylm.soul_lab_app.create_app(config_path)
```

It calls the existing Core application factory and adds Lab-specific middleware/routes to the returned FastAPI application.

Core routes such as:

```text
/healthz
/v1/models
/v1/chat/completions
```

remain Core-owned routes.

Management access refusal must not change the existing Core route behavior.

## Local access gate

Every management response requires both:

```text
configured RelayLM listen host is loopback
AND
actual ASGI transport peer is loopback
```

The configured-host decision is calculated from:

```text
config.listen.host
```

The peer-host decision is calculated from:

```text
request.client.host
```

when an ASGI client is available.

A missing peer is treated as a non-loopback peer.

## Exact refusal response

When either loopback condition is false, the management request fails with:

```text
HTTP 403
```

and exact detail:

```text
lab_management_requires_loopback_access
```

The JSON response shape generated by FastAPI is therefore:

```json
{
  "detail": "lab_management_requires_loopback_access"
}
```

No management projection is returned.

## What is not locality proof

The current locality gate does not trust these as proof of loopback transport:

- `Host` header;
- `Origin` header;
- forwarded headers;
- query parameters;
- browser declarations;
- route labels;
- configured endpoint labels.

The actual ASGI peer and validated configured listen host are the current inputs.

## Loopback host classifier

The current helper is:

```text
is_loopback_host(host: str) -> bool
```

It first strips whitespace and lowercases the host.

The literal:

```text
localhost
```

is accepted.

Bracketed IPv6 literals have one surrounding `[` / `]` pair removed before IP classification.

Other values are passed to Python IP-address classification and accepted exactly when the address reports `is_loopback=true`.

Invalid non-IP names return false.

## Loopback examples covered by current evidence

Current focused evidence requires true for:

```text
127.0.0.1
127.0.0.2
::1
[::1]
localhost
```

and false for:

```text
0.0.0.0
::
relaylm.local
```

The examples do not create an independent host allowlist; the helper behavior above remains authoritative.

## Management cache boundary

Successful management routes return:

```text
Cache-Control: no-store
```

This applies to both exact management-read routes.

The contract does not authorize persistent browser caching of these projections.

## Read-only route boundary

The two current routes are GET-only:

```text
GET /lab/api/settings
GET /lab/api/characters
```

The current focused smoke verifies that mutation-shaped requests to these same route paths are not accepted:

```text
PATCH /lab/api/settings   -> 405
POST  /lab/api/characters -> 405
```

There is no settings-write or registry-write method hidden behind these two endpoints.

## Runtime component projection

No component projection asserts liveness merely from configured state.

## RelayLM Core component

The first current settings component represents RelayLM Core with:

```text
component_id = relaylm
label = RelayLM Core
state = configured
capability = openai_compatible_proxy
```

Its projected endpoint is constructed from the validated listen host and port:

```text
http://<display-host>:<port>/v1
```

IPv6 hosts are bracketed for display when needed.

Its `model_labels` are the sorted configured model-route keys.

## Backend components

The builder emits one backend component for each configured backend ID in sorted backend-ID order.

Its current fields include:

```text
component_id = backend:<backend_id>
label = Backend <backend_id>
state = configured
capability = chat_completions
endpoint = redacted endpoint projection
model_labels = sorted unique model labels
```

The model-label set is the union of:

- the backend's configured default model when present;
- every route `backend_model` targeting that backend when present.

No network probe is performed.


This is management metadata only. It does not execute TTS or claim provider health.

## Avatar component

The current settings builder appends an avatar component with:

```text
component_id = avatar
label = Avatar Adapter
state = unconfigured
capability = avatar_adapter_not_configured
```

This is management metadata only and does not execute an avatar adapter.

## Backend endpoint redaction

The current endpoint projection helper parses a configured backend URL and allows only `http` or `https` with a valid hostname.

When safe parsing succeeds, the projected endpoint retains only:

```text
scheme
hostname
optional port
path with trailing slash removed
```

It discards:

- URL username;
- URL password;
- query string;
- fragment.

IPv6 host display is bracketed when necessary.

## Invalid backend endpoint degradation

If endpoint parsing fails, the scheme is unsupported, or no hostname is available, the public endpoint becomes the literal bounded label:

```text
configured
```

The raw value and parse exception are not returned.

## No backend health inference

The current management settings builder does not contact a backend.

Therefore:

```text
state = configured
```

means configuration metadata exists. It does not mean reachable, authenticated, healthy, loaded, or capable of completing a request.

The top-level and per-component `network_probe_performed` values remain false.

## Character population

The current character projection includes the union of:

```text
all keys in config.characters
PLUS
all non-empty route.character_id values
```

A route may therefore cause a referenced character ID to appear even when the corresponding configured character source object is absent.

Such a character is projected as incomplete rather than silently omitted.

## Route-derived character metadata

For every model route with a non-empty `character_id`, the builder accumulates by character:

```text
route_models
backend_ids
modes
memory_namespaces when present
```

The route-mode value is:

```text
route.mode when present
otherwise config.mode
```

Each collection is de-duplicated and emitted sorted.

## Source-configuration booleans

For a character present in `config.characters`, the current item derives only presence booleans from configured source-path strings.

The current fields are:

```text
soul_configured
output_policy_configured
relationship_anchor_configured
memory_seed_configured
stable_memory_summary_configured
```

The checks use nonempty stripped configured values.

The underlying path strings are not returned.

## Source completeness

Current `source_complete` is exactly:

```text
soul_configured
AND
output_policy_configured
AND
relationship_anchor_configured
```

`memory_seed_configured` and `stable_memory_summary_configured` do not participate in this exact current completeness predicate.

A projected `source_complete=true` reports configured required-source presence only. It does not prove file readability, parser validity, Character Workspace compilation, or runtime admission.

## Incomplete referenced character behavior

When a route refers to a character ID not present in `config.characters`, the character remains in the projection with its route-derived labels and source booleans false.

This preserves the configuration inconsistency for human visibility without leaking source paths or silently hiding the route reference.

## Projection ordering

The current character item list is emitted in sorted character-ID order.

Each route/backend/namespace/mode list is also sorted.

This makes the management read deterministic for the same validated configuration.

## Content and path exclusion

The exact management projections do not include:

- persona/SOUL source body;
- OUTPUT_POLICY source body;
- relationship-anchor source body;
- memory seed body;
- stable-memory summary body;
- persona source path;
- memory source path;
- raw trace path;
- prompt/context body;
- transcript/message body;
- memory record body;
- backend API key.

The character projection exposes only booleans for source configuration/completeness plus bounded route labels.

## Credential and URL secret exclusion

The settings projection must not include backend API keys.

The backend endpoint projection must not include:

- URL username;
- URL password;
- URL query credentials or tokens;
- URL fragment data.

Current focused evidence constructs all of these secret-bearing inputs and verifies their absence from serialized output.

## Trace exclusion

Even when runtime trace is configured with a private path, the management settings projection does not return that path or raw trace data.

Diagnostics remain content-free bounded metadata.

## Management route success behavior

With valid loopback configuration and loopback peer:

```text
GET /lab/api/settings
```

returns the JSON serialization of:

```text
build_lab_settings_projection(config)
```

and:

```text
GET /lab/api/characters
```

returns the JSON serialization of:

```text
build_lab_characters_projection(config)
```

Both use Pydantic model JSON-mode dumping and add `Cache-Control: no-store`.

## Projection builders are read-only

The two current builder functions are:

```text
build_lab_settings_projection(config)
build_lab_characters_projection(config)
```

They derive models from one validated `RelayLMConfig` object.

They do not:

- write configuration;
- create/delete characters;
- inspect or write persona files;
- inspect or write memory files;
- contact backends;
- contact TTS/avatar engines;
- start/stop a process;
- invoke RelayMEM or RelaySLP mutation.

## Core route isolation

The current focused smoke verifies that a management refusal still leaves Core endpoints independently available:

```text
GET /healthz -> normal Core response
GET /v1/models -> Core route remains available
```

The management loopback rule must not be generalized into an accidental replacement policy for all Core routes.

## Static UI boundary

This contract does not own static UI bundle serving or Vite development behavior.

The historical A7 handoff records the local development proxy topology, but the exact management server contract begins at the ASGI Lab routes.

## Browser acceptance boundary

The A7 browser integration treats the settings and characters responses as one management bundle.

Stable exact-consumption rules recorded by the current A7 handoff are:

```text
both schemas validate exactly
AND
settings.listen.loopback_only == true
  -> accept server management bundle

HTTP/access/schema/type/key/locality failure
  -> discard server bundle
  -> explicitly labeled browser-local fallback
```

The browser must not combine one trusted server response with one mock/fallback response into a mixed-authority bundle.

This contract does not own React component hierarchy or fallback visual copy.

## Exact-key browser principle

The current A7 boundary requires allowlisted exact object keys rather than permissive partial schema consumption.

Unexpected fields, missing required fields, type mismatches, enum/value mismatches, or a loopback-only mismatch invalidate the server management bundle for browser use.

This principle prevents newly added server-private fields from becoming implicitly trusted by the browser before an explicit contract revision.

## Reload/stale-state rule

The current A7 browser integration clears stale server state before a reload/read revalidation.

A failed refreshed read therefore does not preserve a prior server-owned management bundle while presenting the current request as successful.

The labeled UI-A6 mock fallback remains non-authoritative.

## Management versus observation

Phase I-2 observation routes may use the same SOUL Lab ASGI wrapper and loopback gate, but their schemas are not part of:

```text
relaylm.lab.settings.v0
relaylm.lab.characters.v0
```

Management settings/characters responses remain content-free even when separate observation APIs expose explicitly governed bounded memory/run information.

No observation field may be retrofitted into the two management schemas without an explicit schema/contract change.

## Management versus mutation

The ASGI wrapper also installs separately owned mutation routes such as Correct, Forget, Pin, held governance, or character creation.

Their presence in the same application does not make them part of this management-read authority.

This contract does not define their request schemas, body limits, confirmation gates, lifecycle transitions, or apply semantics.

## No mutation fallback

Failure to obtain a management projection does not authorize the browser to infer or mutate server state from local mock data.

The safe direction is:

```text
server management bundle unavailable/invalid
  -> discard server bundle
  -> show explicit non-authoritative fallback
```

not:

```text
mock/browser state
  -> treat as server configuration
  -> perform privileged action
```

## No credential fallback

A missing/unconfigured backend or management failure does not authorize browser credential collection or direct backend connection.

Credential ownership remains server/adapter-side.

## Fail-closed invariants

The exact current management-read invariants include:

1. both configured host and actual peer must be loopback before a management projection is released;
2. Host/Origin/forwarded/query/browser claims cannot substitute for peer locality;
3. denied management reads return only bounded 403 detail;
4. management responses are no-store;
5. management route methods are read-only;
6. no network probe is performed while constructing settings projection;
7. configured backend endpoints are secret-redacted before projection;
8. malformed/unsupported endpoint values degrade to `configured` rather than leak raw input or errors;
9. backend API keys never enter management models;
10. persona/memory/trace paths and source content never enter management models;
11. route-referenced incomplete characters remain visible rather than being silently normalized away;
12. source completeness means required source strings are configured, not that source files were opened or validated;
13. browser consumption must reject schema/key/type/locality mismatch rather than partially trusting data;
14. management failure cannot elevate mock browser state into server authority;
15. this read boundary cannot call mutation APIs as a fallback.

This contract does not retire the server implementation, frontend integration, smoke evidence, or broader SOUL Lab architecture sources. Any further source retirement remains a separate bounded transaction with exact provenance, consumer repair, and migration disposition.
